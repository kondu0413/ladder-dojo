### 見つけて直した不具合(改善 4)

CI の E2E が不定期に落ちていたのを追いかけて、**本物の不具合**に行き着いた。2 段階で直している。

1. **テスト側の競合**(先に直した分)。進捗(S-002)と提出回路(S-007)はサーバーへ投げっぱなしで送っているのに、テストがその直後に `page.goto()` で移動したり `context.close()` したりしていた。送信中のリクエストごと消える。`e2e/sync.ts` に `waitForPost` を用意して、移動する前に完了を待つようにした。投げっぱなしは画面としては正しい(判定の表示を待たせない)ので、直すのはテスト側

2. **アプリ側の取りこぼし**(こちらが本命)。待つようにしたら、今度は待っても POST が来ないケースが出た。調べると、**ページを開いた直後に「答え合わせ」を押すと、ログイン済みでも進捗が端末にしか記録されず、提出回路は黙って捨てられていた**。セッションの確認が終わるまで `useSession()` の `user` は null で、その時点で行き先を決めてしまっていたのが原因。確認中(`isPending`)は「ログイン済みかどうかまだ分からない」のであって「未ログイン」ではない
   - `ProgressProvider` に控えを持たせ、確認が済むまで書き込みを預かって、決まってから流すようにした
   - 提出も同じ判断が要るので、ページから `api.submit` を直接呼ぶのをやめ、`recordSubmission` として context にまとめた
   - 再現テストを足した。`/api/auth/get-session` をわざと 1.5 秒遅らせ、確認中に押しても両方サーバーに届くことを確かめる。控えを外すとこのテストは 30 秒でタイムアウトして落ちることを確認済み

**反省**: 1 回目は「テストの書き方が悪い」で止めてしまった。CI が落ちたときに「テストが悪い」で片付けると、その裏の不具合を見逃す。

### 見つけて直した不具合(フェーズ2)
- **検索が日本語 17 文字以上で 500 になっていた**。SQLite の `LIKE` にはパターン長の上限(既定 50 バイト)があり、`D1_ERROR: LIKE or GLOB pattern too complex` で落ちていた。E2E は通っていたが、サーバーログにだけ出ていたので気づいた。`instr()` による部分一致に変更した。合わせて、`%` や `_` を含む検索語がワイルドカードとして解釈される問題(「100%」で全件ヒット)も解消した。長い日本語の検索語・タグ、`%` / `_` を含む検索語の API テストを追加
- 検索条件を素早く切り替えると、前のリクエストが中断されてサーバーのエラーログを汚していた。クライアントで `AbortController` を使って明示的に止め、中断されたリクエストはサーバーもエラー扱いしないようにした
- エラーログに Drizzle のメッセージ(SQL とバインド値 = 利用者の検索語)が入っていたので、原因だけを出すようにした
