### D-001 言語: TypeScript(strict)

- **採用**: TypeScript、`strict: true`、`noUncheckedIndexedAccess: true`
- **理由**: §6「型のある言語」。ブラウザで動くシミュレータはJS系が唯一の現実的選択。フロント・コア・サーバー(Workers)・テストを1言語で書ける
- **却下**: Rust + WASM(シミュレータ部分)。性能は不要(ラング数は数十規模)、ツールチェーンが増え自律開発の速度が落ちる。Kotlin/JS、Dart(Flutter Web)はエコシステムと無料ホスティングの相性で不利

### D-002 リポジトリ構成: pnpm workspace モノレポ(2026-09-14 改訂)

- **採用**:
  ```
  packages/core   … シミュレータ・判定・回路JSONスキーマ。依存ゼロ(zodのみ)、DOM非依存・Node API 非依存
  apps/web        … React アプリ(Vite)。core を import する。ビルド成果物 dist/ を Worker の静的アセットとして配信
  apps/api        … Cloudflare Worker(Hono + Better Auth + Drizzle)。wrangler.jsonc、D1 マイグレーション、API テストを持つ
  ```
- **理由**: §6「判定ロジックとシミュレータは共通のコア」を**パッケージ境界**で強制する。core は Node(Vitest)・ブラウザ・Workers のどこでも動く純TSにし、フェーズ2の投稿時サーバー側検証で `apps/api` が同じコードを import する
- **改訂内容**: `supabase/`(migrations, seed)を廃止し、`apps/api` に統合。API のルート定義の型を `apps/web` が Hono RPC で参照するため、`apps/web` は `apps/api` の**型のみ**に依存する(実行時コードは import しない。Biome の `noRestrictedImports` で禁止)
- **却下**: 単一パッケージ + `src/core` ディレクトリ。境界がlint頼みになり、UI依存が混入しやすい。モノレポのコストは pnpm なら小さい

### D-003 フロントエンド: Vite + React 19 + React Router(SPA)

- **採用**: SPA。SSRなし。ビルド成果物は静的ファイルのみ
- **理由**:
  - シミュレータはクライアント側で動くため SSR の恩恵がほぼない。静的ファイルならどの無料ホスティングにも置けて、ホスティング乗り換えが設定変更だけで済む
  - React はモバイルタッチ操作の実装例・ライブラリが最も豊富で、Claude Code の生成精度も高い
  - フェーズ2の「投稿問題一覧」は検索エンジン流入を狙わない(ログイン前提の学習アプリ)ため SEO 要件なし
- **却下**:
  - Next.js: SSR/Server Actions が不要。Node ランタイムに縛られ、無料ホスティングが実質 Vercel(Hobby は非商用限定)に寄る
  - SvelteKit / Nuxt: 技術的には十分だが、エコシステム規模とモバイルUI部品の選択肢で React に劣る
  - Remix / TanStack Start: 同上(サーバー前提)

### D-004 UI: Tailwind CSS v4、ラダー図は SVG

- **採用**: Tailwind CSS v4(モバイルファースト)。ラダー図の描画は SVG
- **理由**: SVG は要素ごとにタップ領域を持てる(接点をタップして操作、グリッドセルをタップして配置)。DOMイベントで済むためドラッグ非依存UIを作りやすく、通電ハイライトも CSS クラス切替で表現できる。テストでも要素を特定しやすい
- **却下**: Canvas(ヒットテストとアクセシビリティを自前実装する必要)、WebGL(過剰)

### D-005 回路データ形式: JSON + zod スキーマ(2026-09-14 一部改訂)

- **採用**: `packages/core` に zod スキーマを置き、`Circuit`(グリッド上の部品と接続)、`TestCase`(入力操作シーケンス → 期待出力)、`Problem`(仕様文 + 模範解答 Circuit + TestCase[] + メタ)を定義。ルートに `schemaVersion` を持たせ、将来のマイグレーション関数を core に置く
- **理由**: §6「問題・模範解答・テストケース・サンドボックス保存がすべて同じ形式」。D1(SQLite)には `TEXT` 列に JSON 文字列として保存し、DBスキーマは回路の内部構造を知らない(問題形式の変更がDBマイグレーションを要求しない)。保存前に API 層で zod 検証し、壊れた JSON は保存しない
- **公式問題の置き場**: DBではなくリポジトリ内の JSON(`apps/web/src/problems/*.json` 相当)としてビルドに同梱。理由: 未ログインでも解ける(§3.5)、D1 の読み取り行数を消費しない、Git で差分レビューできる。投稿問題(フェーズ2)のみ DB に置く
- **2026-09-15 追記(記述形式)**: 公式問題は素の `.json` ではなく **TypeScript モジュール**(`apps/web/src/problems/*.ts`)で書く。中身・スキーマ・ビルドへの同梱のされ方は JSON と同じで、次の利点がある:
  - `packages/core` のビルダー(`ladder().row(no("X0"), out("Y0"))`)で回路を書けるので、セル座標を手で並べるより読みやすく、間違えにくい
  - 型チェックが効く(デバイス名の綴り間違い、存在しない命令などがコンパイル時に落ちる)
  - `apps/web/src/problems/problems.test.ts` が全問について「スキーマを満たす」「**模範解答が自分のテストケースをすべて通る**」「直す問題の初期回路は必ずどれかのテストで落ちる」「読む問題のシナリオが例外なく流せる」を毎回検証する(SPEC.md §2.4「問題の判定ロジックはテスト必須」)
  - フェーズ2 の投稿問題(DB 保存)は JSON のまま。同じ zod スキーマを共有する

### D-006 認証・DB: Cloudflare D1 + Drizzle + Better Auth(**差し戻し → D1 採用、2026-09-14**)

- **経緯**: 2026-09-05 に Supabase(Auth + Postgres + RLS)を採用し、D1 構成を「乗り換え第一候補」としていた。2026-09-14 に人間が D-006 を差し戻し、**Supabase をやめて Cloudflare に一本化**することを決定
- **採用**: Cloudflare Workers(Static Assets)+ Hono + D1 + Drizzle ORM + Better Auth。すべて Cloudflare の Workers Free プラン内で動かす(カード登録不要)
  - 認証: Better Auth を Worker 上で動かす。Google ログインのみ(D-007)。セッションは D1 の `session` テーブルに保存し、Cookie(HttpOnly, Secure, SameSite=Lax)で保持。SPA と API が同一オリジンなので CORS・トークン受け渡しが不要
  - DB: D1(SQLite)。スキーマは Drizzle で TypeScript から定義し、drizzle-kit で SQL マイグレーションを生成(D-018)
  - 権限: RLS がないため、**すべてのデータアクセスを API 経由**にし、権限判定を API 層で行う(D-017)。ブラウザから DB に直接触る経路は存在しない
- **理由(人間の決定を踏まえた技術的な裏付け)**:
  - **ベンダーが1つ**になり、人間のセットアップ作業が Cloudflare・Google Cloud・GitHub の3か所だけで済む(SETUP.md)。Supabase の dev/prod 2プロジェクト運用、7日間無アクセスでの一時停止、keep-alive ワークフロー、SMTP 設定がすべて不要になる
  - **ローカルで完結する開発・テスト**: Wrangler(Miniflare)がローカル D1 を提供するため、E2E テストにクラウドの dev 環境が要らない(D-014)。CI が外部サービスに依存せず、シークレットなしで PR の CI が回る
  - D1 の無料枠は容量 5 GB / アカウント、Time Travel(7日間の時点復元、要確認)があり、Supabase 無料枠(500 MB、バックアップなし、7日停止)より運用が楽。ただし **1 データベースあたりの上限は 500 MB(Free、要確認)** なので、容量面の実質的な余裕は Supabase と同程度。詳細は COST.md
  - 自前実装が増える点(旧却下理由)は、Better Auth(認証)と Hono ミドルウェア(権限)で吸収する。その分を API テスト(D-011、SPEC.md §2.4)で担保する
- **失うもの(認識した上で受け入れる)**:
  - Postgres 固有機能(RLS、`pg_cron`、マテリアライズドビュー、ウィンドウ関数の一部)。集計は Cron Triggers + 集計テーブルで代替(D-010)
  - Supabase Auth の管理画面(ユーザー一覧・BAN 等)。必要になれば管理 API を自作
  - 全 API リクエストが Workers 無料枠(10万 req/日)と D1 の読み書き上限に乗る。縮退方針は COST.md
- **却下(2026-09-05 時点の比較を保持)**:
  - Supabase: 2026-09-05 採用 → **2026-09-14 差し戻し**。ベンダー分散と dev/prod 2プロジェクト運用・一時停止対策の負担が理由
  - Firebase(Firestore + Auth): NoSQL のため、組織内ランキング・つまずき集計・権限の交差条件を書くのが困難。集計は Cloud Functions 必須で従量課金プラン(Blaze)が必要
  - Neon + Clerk(または Auth.js): DB と認証が別ベンダー。D1 + Better Auth と同じく API 経由が必須なのに、ベンダーだけ増える
  - Convex: 独自クエリ言語・独自ホスティングでロックインが強い
  - PocketBase: 常駐サーバーが必要で 0円ホスティングがない

### D-007 認証方式: Google ログインのみ(2026-09-14 改訂)

- **採用**: フェーズ1は **Google ログインのみ**。Better Auth の `socialProviders.google` を使い、メール送信を一切行わない
- **保留(人間の判断待ち、着手しない)**: メール/パスワード認証(会社メールで使いたい企業導入・Google アカウントを持たない層向け)。2026-09-05 の暫定案では併用としていたが、2026-09-14 に人間が「フェーズ1では実装しない」と決定。実装する場合は Better Auth の `emailAndPassword` を有効化し、確認メール・パスワードリセット用の送信手段(D-008)が必要になる
- **却下(据え置き)**: Magic Link(メール消費が多い)、GitHub ログイン(対象ペルソナに合わない)
- **UI 上の扱い**: ログイン画面は「Google でログイン」ボタン1つ。未ログインでも公式問題・サンドボックスは使える(§3.5、S-002)
- **E2E テストでのログイン**: Google の画面は CI で通せないため、D-014 の「E2E 専用ログイン」を使う

### D-008 SMTP: 保留(2026-09-14 改訂 / 2026-09-16 再調査)

- **保留**: メール/パスワード認証を実装しない(D-007)ため、SMTP は不要
- **削除した作業**: SETUP.md の Brevo 節、COST.md の Brevo 節、`.env.example` の SMTP 関連コメント
- **2026-09-16 再調査(改善候補 7「通知」のため)**: 当時の前提が 2 つとも変わっていた。**この項の「Brevo は独自ドメイン不要」は、もう成り立たない**
  - **`workers.dev` からはメールを送れない**。SPF / DKIM の DNS レコードを置けないため(Cloudflare 自身のドキュメントに明記)。これが本当の障壁で、送信サービスの選択以前の問題
  - 2024 年 2 月以降、Gmail / Yahoo / Microsoft が送信ドメインの認証を必須にした。**認証が無いと Brevo は差出人を `@brevosend.com` に書き換える**。届きはするが、受け取る側から見て誰からのメールか分からず、製品の通知としては使えない
  - MailChannels の Workers 向け無料枠は **2024 年に終了**
  - Cloudflare Email Sending は 2026-04 に public beta。**Workers Paid($5/月)必須で無料枠なし**
  - **結論**: メール通知には独自ドメイン(年 1,000〜2,000 円)が要る。送信サービス自体はドメインさえあれば Resend の無料枠(3,000通/月)で 0円。COST.md の提案 #1 に書いた
- **メールを使わない道がある(S-019)**: Web Push は外部サービスが要らず 0円。すでに PWA と Service Worker がある(S-013)ので土台は揃っている

### D-009 ホスティング: Cloudflare Workers(Static Assets)(2026-09-14 改訂)

- **採用**: Cloudflare Pages ではなく **Workers(Static Assets)** を使う。`apps/api/wrangler.jsonc` で `assets.directory = "../web/dist"`、`assets.not_found_handling = "single-page-application"`、`assets.run_worker_first = ["/api/*"]` を設定し、SPA と API を **1 つの Worker**(名前 `ladder-dojo`)で配信する。URL は `https://ladder-dojo.<サブドメイン>.workers.dev`
- **理由**:
  - Cloudflare が新規プロジェクトに Workers を推奨しており、Pages Functions より D1 バインディング・Cron Triggers・`wrangler dev` の統合が素直
  - 静的アセットへのリクエストは **無料・無制限で Workers の 10万 req/日 に数えない**(要確認)。`run_worker_first` で `/api/*` だけ Worker を通すため、画面表示・シミュレータ利用は無料枠を消費しない
  - SPA と API が同一オリジンになり、Better Auth の Cookie セッションがそのまま使える
  - 商用利用の制限がない(Pages と同じ)。カード不要
- **却下**:
  - Cloudflare Pages + Pages Functions: 2026-09-05 採用 → 2026-09-14 変更。Pages でも D1 は使えるが、Pages Functions は `_worker.js` 形式で Hono・Cron Triggers・vitest-pool-workers との組み合わせに一手間ある。Cloudflare 自身が Workers への移行を案内している
  - 静的ホスティングと API Worker を分ける構成: オリジンが分かれ、Cookie 認証に CORS と `SameSite=None` が必要になる。1 Worker で済むものを分ける理由がない
  - Vercel / Netlify / GitHub Pages / Firebase Hosting: 2026-09-05 の却下理由のまま

### D-010 サーバー側ロジックの置き場: Hono API on Workers(2026-09-14 改訂)

- **採用**: 「サーバー側コードを書かない」方針を撤回し、**データアクセスはすべて `apps/api` の Hono API 経由**にする。構成:
  - `GET/POST /api/auth/*` … Better Auth のハンドラ(Google ログイン開始・コールバック・セッション取得・ログアウト)
  - `/api/progress`, `/api/submissions`, `/api/sandbox` … フェーズ1(本人のデータのみ)
  - `/api/problems`(投稿問題)… フェーズ2
  - `/api/rankings`, `/api/orgs/*` … フェーズ3
  - すべてのルートは zod で入力検証し、D-017 の権限ミドルウェアを通す
- **フェーズ別の見立て**:
  - フェーズ1: 進捗・提出・サンドボックスの CRUD。すべて「本人のデータのみ」(`user_id = session.user.id` を API 側で強制)
  - フェーズ2: 投稿時の「模範解答がテストケースを全て通るか」の自動チェックは、クライアントで即時実行しつつ、**公開フラグを立てる API がサーバー側で `packages/core` を使って再実行**する(改ざんされた投稿が公開されないようにする)。CPU 時間 10 ms/リクエストの制約があるため、テストケース数・スキャン数に上限を設ける(COST.md)。クリア率・いいね数は集計列(カウンタ)を更新して持つ
  - フェーズ3: ランキングは **Cron Triggers**(無料)で期間別集計を `ranking_snapshots` テーブルに書き出す。連続学習日数は `activity_days` から計算。組織権限は D-017
- **却下**:
  - Postgres 関数 / RLS / `pg_cron` / マテリアライズドビュー: D1 に存在しない
  - Cloudflare Durable Objects: 無料枠にあるが、フェーズ3までの要件は D1 + Cron で足りる。リアルタイム要件が出た時点で再検討
  - Supabase Edge Functions(Deno): Supabase 廃止に伴い不要

### D-011 テスト基盤: Vitest + vitest-pool-workers + Playwright(2026-09-14 改訂)

- **採用**:
  - Vitest(`packages/core`): スキャン順序、タイマ、カウンタ、自己保持、微分、判定のユニットテスト。カバレッジは core で 90% 以上を目標
  - **Vitest + `@cloudflare/vitest-pool-workers`(`apps/api`)**: workerd 上で実 D1(ローカル・インメモリ)を使って API を直接呼ぶテスト。**権限判定は必須テスト対象**(SPEC.md §2.4 に追記済み、D-017 にテスト観点を列挙)。マイグレーションはテスト前に自動適用
  - Playwright(`apps/web`): 主要フロー(問題を開く → 回路を操作/編集 → 判定 → 模範解答表示 / ログイン → 保存 → 再読込で復元)。デバイスプロファイルは **Pixel 7 相当のモバイル**と Desktop Chrome の2つ。接続先は `wrangler dev` が起動したローカル Worker(ビルド済み SPA + ローカル D1)。D-014 参照
  - React Testing Library: 部品単位の UI テストに限定して使う
- **理由**: Vitest は Vite と設定を共有できて速い。vitest-pool-workers は本番と同じ workerd ランタイムと D1 の SQL 方言で API を検証でき、モックの乖離がない。Playwright はモバイルエミュレーションとタッチイベントを標準サポートし、§4 DoD「スマホのブラウザで操作できる」を CI で検証できる
- **却下**: Jest(ESM/TS 設定が重い)、Cypress(モバイルエミュレーションが弱い)、D1 を better-sqlite3 でモックする案(SQL 方言・バインディングの差で本番と乖離する)

### D-012 CI/CD: GitHub Actions + Wrangler(2026-09-14 改訂)

- **採用**:
  - `ci.yml`(push / PR): lint → typecheck → unit(core)→ API テスト(ローカル D1)→ build → E2E(ローカル Worker + ローカル D1)。**外部サービスにアクセスしないため、PR の CI にシークレットは不要**
  - `deploy.yml`(`main` で CI 通過後): `wrangler d1 migrations apply ladder-dojo --remote` → `wrangler deploy` → `wrangler secret bulk`(GitHub Secrets から Worker のシークレットを同期)。使う Secrets は `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` / `BETTER_AUTH_SECRET` / `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` の 5 つ(SETUP.md §3)
  - `backup.yml`(週1回): `wrangler d1 export --remote` の出力を圧縮して Actions アーティファクトに保存(保持 4 世代)。D1 の Time Travel(7日、要確認)の補完
  - 廃止: `db-migrate.yml`(deploy に統合)、`keepalive.yml`(D1 は一時停止しない)
- **マイグレーションの安全策**: 本番マイグレーションに人間の手動承認は置かない(§2.1 の自律サイクルを止めないため)。代わりに (1) 破壊的変更(列削除・型変更)は「追加 → コード切替 → 次のリリースで削除」の2段階に分ける、(2) `wrangler d1 migrations apply --local` を CI の API テストで毎回通す、(3) 失敗時は Time Travel で復元する、の3点で担保する
- **理由**: §2.4「CIでテストが通らない状態で次に進まない」を**デプロイのゲート**として実装するため、デプロイは CI の後段に置く。Cloudflare の Git 連携(Workers Builds)はテスト失敗でもデプロイされてしまうため使わない
- **プレビューデプロイ**: 行わない。Workers のプレビュー URL は本番と同じ D1 バインディングを共有するため、PR の検証はローカル E2E で行う(D-014)。必要になれば `ladder-dojo-preview` Worker + 別 D1 を追加する
- **前提**: ~~リポジトリは private のため Actions は月 2,000 分~~ → 2026-09-15 にリポジトリは public と確認。Actions の分数制限なし
- **2026-09-15 追記(人間の指示: Secrets を 3 つに減らす)**:
  - GitHub Secrets は **`CLOUDFLARE_API_TOKEN` / `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` の 3 つだけ**。以前の 5 つから `CLOUDFLARE_ACCOUNT_ID` と `BETTER_AUTH_SECRET` を外した
  - **アカウント ID**: `.github/actions/cloudflare-setup`(composite action)が `wrangler whoami` の出力から 32 桁 16 進の ID を正規表現で拾い、`CLOUDFLARE_ACCOUNT_ID` 環境変数としてジョブ内にだけ流す(ログはマスク)。トークンが複数アカウントに紐づく場合は最初の 1 つを使う
  - **D1 の作成と ID 反映**: 同 action が `wrangler d1 list --json` で `ladder-dojo` を探し、無ければ `wrangler d1 create ladder-dojo --location apac` で作る。得た ID で `apps/api/wrangler.jsonc` のトップレベル `d1_databases[0].database_id` を **CI の作業コピー上でだけ**書き換える(コミットしない)。リポジトリ上の値はプレースホルダのままでよく、ローカル(`wrangler dev` / vitest / E2E)はプレースホルダで動く。理由: CI からのコミットバックは push 権限とループ防止が必要で、実行時置換の方が単純。`env.e2e` 側の `database_id` はローカル専用なので触らない
  - **`BETTER_AUTH_SECRET`**: `deploy.yml` が `wrangler deploy` の後に `wrangler secret list --format json` を見て、未登録なら `openssl rand -base64 32` で生成し `wrangler secret bulk` で登録する(初回のみ。以後は既存値を維持)。値は誰も保管しない。作り直す場合は Cloudflare ダッシュボードで削除して再デプロイ。初回デプロイでは Worker が数秒間シークレット無しで公開されるが、認証を lazy 初期化にして落ちないようにする
  - **順序**: CI(workflow_call)→ build → cloudflare-setup → `d1 migrations apply --remote`(`migrations/*.sql` がある場合のみ)→ `wrangler deploy` → secrets 同期。`ci.yml` は main 以外の push と PR で直接動き、main では `deploy.yml` から呼ばれる(二重実行しない)
  - **`backup.yml`** も同じ composite action でアカウント ID と D1 ID を解決してから `wrangler d1 export --remote` する。保持 28 日(週次 4 世代)

### D-016 追記: Hono RPC をやめて DTO 型の共有にした(2026-09-15)

- **やろうとしたこと**: `apps/web` が `import type { AppType } from "@ladder-dojo/api"` して `hc<AppType>()` を使う
- **起きた問題**: `AppType` は Hono の `Bindings`(= `Env`)を含み、`Env` は `D1Database` / `Fetcher` という **Cloudflare Workers のグローバル型**を参照する。`@cloudflare/workers-types` はモジュールではなくグローバル宣言ファイルなので、`apps/web` 側でこれを読ませるには tsconfig の `types` に足すしかない。すると `Response` / `Request` / `Headers` などが DOM の型と二重定義になる
- **採用**: `apps/api/src/dto.ts` に **レスポンスの型だけ**を置き、`@ladder-dojo/api/dto` として types のみ公開する。このファイルは Workers のグローバル型を一切参照しない。ハンドラは返り値にこの型を注釈するので、web と API の型がずれるとコンパイルで落ちる。呼び出しは素の `fetch`(同一オリジンなので Cookie はそのまま送られる)
- **失うもの**: パスとメソッドの型安全(`/api/progres` のような綴り間違いはコンパイルで防げない)。API 8 本ぶんのクライアント関数を手で書く手間。いずれも E2E テストが実 API を叩いて担保する
- **却下**: `apps/web` の tsconfig に `@cloudflare/workers-types` を足す(DOM 型と衝突)、`skipLibCheck` に頼る(衝突は型解決の時点で起きるので効かない)、OpenAPI からの型生成(ツールが増える)

### D-017 権限判定は API 層で行う(RLS の代替)(2026-09-14 新設)

- **採用**: D1 には行レベルセキュリティがないため、**すべての権限判定を `apps/api` の Hono ミドルウェアと各ハンドラで行う**。方針:
  1. **DB への経路は API のみ**。ブラウザは D1 に触れない(バインディングは Worker にしかない)
  2. **認証ミドルウェア** `requireUser`: Better Auth のセッション Cookie を検証し、`c.var.user` を設定。未ログインは 401
  3. **本人性の強制**: フェーズ1のデータ(進捗・提出・サンドボックス)は、リクエストボディの `user_id` を信用せず、常にセッションの `user.id` でクエリを絞る。他人の ID を指定しても 404(存在を漏らさない)
  4. **組織ミドルウェア**(フェーズ3): `requireOrgMember(orgId)` / `requireOrgAdmin(orgId)`。`org_members(org_id, user_id, role)` を1クエリで引き、メンバー外は 404、メンバーだが管理者でない場合は 403
  5. **可視性の判定**(フェーズ2/3): 投稿問題の `visibility`(public / org / private)と通報による非表示は、一覧・取得の両方の SQL の WHERE 句に必ず入れる(取得側だけの判定にしない)
  6. **管理者の閲覧範囲**: 管理者が見られるのは「自分が管理者である組織のメンバー」のデータのみ。組織横断の一覧 API は作らない
- **品質基準(SPEC.md §2.4 に追記済み)**: 上記の各ルールに対して、vitest-pool-workers による API テストを必須とする。最低限のテスト観点:
  - 未ログインで保護ルートを叩くと 401
  - 他人の `user_id` / リソース ID を指定した取得・更新・削除が 404 で、DB が変更されない
  - 組織メンバー外 → 404、メンバー(非管理者)→ 403、管理者 → 200(閲覧系・割り当て系それぞれ)
  - 組織 A の管理者が組織 B のメンバーの進捗を取得できない
  - `visibility = org` の問題が、他組織のユーザーの一覧・取得の両方に現れない
  - 通報で非表示になった問題が一覧・取得に現れない
  - 本番設定(`E2E_AUTH_BYPASS` 無し)でメール/パスワードのエンドポイントが無効
- **理由**: RLS は「書き忘れても DB が守る」安全網だったが、D1 では API がその役割を負う。テストを品質基準に組み込むことで、ハンドラ追加時の書き忘れを CI で検出する
- **2026-09-15 実装時の追記**:
  - フェーズ1 の観点(未ログイン 401、他人のリソースは 404 で DB も変わらない、ボディの `user_id` を信用しない、壊れた回路 JSON を保存しない)を `apps/api/test/permissions.test.ts` に実装済み。組織まわり(方針 4〜6)はフェーズ3 で追加する
  - 所有者チェックは「取得してから比べる」のではなく **すべてのクエリの `WHERE` に `user_id` を入れる**方式にした。更新・削除は `.returning()` が 0 件なら 404 を返すので、比較のし忘れが起きにくい
  - `requireUser` はセッション取得が例外を投げた場合(シークレット未設定・壊れた Cookie)も未ログイン扱いにして 401 を返す。500 を返すと存在の手がかりになるため
  - **テスト環境の注意**: `@cloudflare/vitest-pool-workers` 0.22 にはテストごとの D1 分離オプションが無く、同一ファイル内のテストはローカル D1 を共有する。件数を数えるアサーションは必ず `user_id` で絞る(`test/helpers.ts` に明記)
- **却下**: D1 の前段に権限判定用の Durable Object を置く案(過剰)。SQL ビューで擬似 RLS(D1 ではセッション変数がなく成立しない)

### D-018 DB スキーマとマイグレーション運用: Drizzle + drizzle-kit + Wrangler(2026-09-14 新設)

- **採用**:
  - スキーマは `apps/api/src/db/schema.ts` に Drizzle(sqlite)で定義。Better Auth のテーブル(`user`, `session`, `account`, `verification`)は `@better-auth/cli generate` で生成したものを同ファイルに取り込む
  - `drizzle-kit generate` で `apps/api/migrations/NNNN_*.sql` を生成し、**ファイルはコミット**する。適用は `wrangler d1 migrations apply`(ローカル `--local` / 本番 `--remote`)。Drizzle の `migrate()` は使わない(Wrangler の `d1_migrations` テーブルと二重管理になるため)
  - フェーズ1 のテーブル(見立て): `user` / `session` / `account` / `verification`(Better Auth)、`progress`(user_id, problem_id, cleared_at, attempts, failures, last_attempt_at)、`submissions`(id, user_id, problem_id, circuit_json, passed, circuit_hash, created_at)、`sandbox_circuits`(id, user_id, title, circuit_json, test_cases_json, updated_at)、`activity_days`(user_id, date_jst)。すべて `user_id` を先頭にした複合インデックスを持つ(D1 は読み取り「行数」課金のため、テーブルスキャンを避ける)
  - D1 の読み書き上限を意識した設計: Better Auth の `session.cookieCache` を有効化(毎リクエストの session 読み取りを減らす)、`session.updateAge` を 1 日にする(毎リクエストの session 書き込みを避ける)、`COUNT(*)` は集計列で代替
- **理由**: TypeScript でスキーマとクエリの型を一元化でき、SQLite 方言の差を Drizzle が吸収する。マイグレーションファイルを Git に置くことで差分レビューと Time Travel 復元時の再適用が容易
- **却下**: Prisma(D1 アダプタはあるがエンジンが重く Worker サイズ 3 MB 制約に近い)、Kysely(可だがスキーマ定義と型生成が別途必要)、生 SQL のみ(型がなく §6「型のある言語」の趣旨に反する)

## 仕様上の暫定判断(SPEC.md に答えがない項目)

### S-001 連続学習日数の「1日」の境界(暫定)

- **論点**: §3.7「連続学習日数」の日付境界をどのタイムゾーンで切るか
- **選択肢**: (a) JST 固定 (b) ユーザー端末のタイムゾーン (c) UTC
- **暫定採用**: (a) JST 固定。UI 言語が日本語のみ(§5)で対象ユーザーも国内のため
- **理由**: サーバー側集計(ランキング)とクライアント表示で結果が一致する。海外展開時に (b) へ変更可能な設計(活動日は日付文字列で保存)にする

### S-002 未ログイン時の進捗の扱い(暫定)

- **論点**: §3.5 で未ログインでも問題を解けるが、その進捗をどう扱うか
- **暫定採用**: ブラウザの localStorage に保存し、ログイン時に「この端末の進捗を引き継ぐ」確認を出してサーバーへマージする(クリア済みは OR、試行回数は加算)
- **理由**: 試してから登録する導線を壊さない。サーバー側で匿名ユーザーを作ると D1 の行数と Workers のリクエストを消費する

### S-004 スキャン内の評価順と「出力は次スキャンに反映」の解釈(暫定)

- **論点**: SPEC.md §3.1 は「上から下・左から右、1スキャンで全ラングを評価、**出力は次スキャンに反映**」とある。この「次スキャンに反映」を、(a) 物理出力の書き出しタイミングと読む(実機の PLC と同じで、コイルの結果は同じスキャンの後続ラングから見える)か、(b) すべてのコイル書き込みを次スキャンまで遅延させる(全ラングが同じ入力像を見る)か
- **暫定採用**: **(a)**。コイルの結果はデバイスに即時書き込み、同じスキャンの後続ラングの接点から見える。外から観測できるのはスキャン境界の値だけなので、(b) と観測結果が変わるのは「ラングの並び順」が効く場合に限られる
- **理由**:
  - 実機(三菱・オムロン等)の動作と一致する。学習アプリとして誤った挙動を教えない
  - (b) だとラングの並び順が結果に一切影響せず、§3.1 の「上から下」という記述と、現場で実際に問題になる「ラングの順番を間違えて 1 スキャン遅れる」という学習ポイントが失われる
  - 物理出力(Y)は END 処理でまとめて反映される、という実機の説明とも矛盾しない
- **判定への影響**: 振る舞い判定(§3.3)は「入力を変えたら状態が落ち着くまでスキャンする(settle)」方式にしたため、ラング順による 1〜数スキャンの伝播遅れで正誤が変わらない。並び順の違いは「指標」としても正誤としても扱わない
- **発振回路の扱い**: settle が 50 スキャンで収束しない回路(例: `b接点 M0 → コイル M0`)は `unstable` として不正解にし、その旨を表示する

### S-005 判定の時間モデル(暫定)

- **論点**: タイマを含む問題をどう判定するか。実時間で待つと 3 秒のタイマ問題のテストに 3 秒かかる
- **暫定採用**: 判定は**仮想時間**で行う。1 スキャン = 10 ms 相当とし、`wait` ステップは指定 ms ぶんスキャンを回す。UI のシミュレータ実行は実時間(§5 の 1x / 5x / 即時 切替はこの上に載せる)
- **理由**: 判定がミリ秒単位で再現可能になり、CI とサーバー側再検証(フェーズ2)の CPU 時間が読める。テストケースの待ち時間合計に 120 秒の上限を設け、1 ケース 50,000 スキャンで打ち切る(COST.md §1.1 の CPU 10 ms/リクエスト対策)
- **テストケースのステップ**: `set`(入力設定)/ `press`(押して離す)/ `wait`(時間を進める)/ `expect`(出力を検証)の 4 種。`set` と `press` の後は時間を進めずに settle する

### S-006 回路 JSON のグリッド表現(暫定)

- **論点**: §3.1 の「部品パレットから接点・コイルをグリッドに置き、線でつなぐ」を JSON でどう表すか
- **暫定採用**: 行 × 列のグリッド。各セルは要素(横線 / 接点 / コイル)と「右端から 1 つ下の行へつなぐ縦線」フラグを持つ。各行の左端は常に左母線につながり、コイルは**最右列にのみ**置けて右母線に直結する。並列(OR)は縦線で、直列(AND)は同じ行に並べて表す
- **理由**: スマホのタップ操作に素直(セルをタップして部品を置く、セル境界をタップして縦線)。ラングは「縦線でつながった行のまとまり」として機械的に決まり、通電判定はノード(セル境界)の幅優先探索で書ける。SVG 描画との対応も 1 対 1
- **却下**: ノード + エッジの一般グラフ(自由度が高すぎ、ラダー図として不正な形を作れてしまう)、命令リスト(IL)形式(見た目と 1 対 1 にならず「直す」モードの編集 UI と噛み合わない)
- **制約**: 最大 16 列 × 64 行。コイルは最右列のみ。最終行から下への縦線は不可。これらは zod スキーマで強制する

### S-003 提出回路履歴の保持上限(暫定)

- **論点**: §3.5「提出回路そのものを履歴として保持」は無制限だと D1 の 1 データベース上限(Free 500 MB、要確認)を圧迫する
- **暫定採用**: 問題ごと・ユーザーごとに **不正解の直近20件 + 正解全件** を保持。同一回路(正規化JSONのハッシュ一致)は重複保存しない
- **理由**: つまずき分析(§3.8)には直近の失敗が重要で、古い失敗は価値が低い。COST.md の縮退方針と連動

### S-007 提出回路を保存するタイミング(暫定)

- **論点**: SPEC.md §3.5 の「ユーザーが提出した回路そのもの(正解・不正解問わず履歴として保持)」は、いつサーバーに送るか。§3.8 の管理者ビューはこの履歴を前提にしている
- **暫定採用**: 「答え合わせ」を押すたびに送る。ログイン中のみ。**await せず投げっぱなし**にして、判定結果の表示は待たせない。送信に失敗しても画面にエラーを出さない
- **理由**: 判定はクライアント側で完結する(§6)ので、送信を待つと答え合わせが遅くなるだけで何も得しない。進捗同期(`record`)が同時に走っていて、通信が切れていればそちらのエラー表示で分かる。提出履歴は学習者本人が直接見るものではなく、管理者の分析用なので、1 件落ちても学習は成立する
- **重複対策**: 同じ回路(指紋一致)はサーバー側で行を増やさない(S-003)ので、同じ回路で答え合わせを連打しても書き込みは 1 回だけ
- **セッション確認中は判断を保留する(2026-09-15 追記)**: `useSession()` の確認が終わるまで `user` は null になる。ここで「未ログイン」と決めてしまうと、ページを開いた直後の答え合わせで進捗が端末にしか残らず、提出は捨てられる。実際にそうなっていた。確認が済むまで書き込みを預かり、行き先が決まってから流す。提出も進捗も同じ判断が要るので、`ProgressProvider` の `recordSubmission` に集約した
- **却下**: クリア時だけ送る(つまずき分析に必要なのは失敗回路なので本末転倒)、一定間隔でまとめて送る(未送信のまま画面を閉じると落ちる)
- **注意**: E2E で「提出したものが管理者から見える」ことを確かめるときは、ページを閉じる前に POST の完了を待つ必要がある(`page.waitForResponse`)

### S-008 組織限定公開の UI(暫定)

- **論点**: SPEC.md §3.8「管理者は組織限定の問題を作れる」の公開範囲を、投稿ダイアログでどう選ばせるか
- **暫定採用**: 公開範囲は 公開 / 組織のメンバーだけ / 非公開 の 3 つ。「組織のメンバーだけ」は**所属組織が 1 つ以上あるときだけ**選択肢に出し、選んだら組織を選ぶ。組織が 1 つならそれを初期選択する
- **理由**: 組織に入っていない人に選ばせても投稿できずに詰まるだけ。SPEC.md は「管理者は作れる」と書いているが、メンバーが組織に問題を出せて困ることはない(むしろ新人同士の問題の出し合いは §3.6 の狙いに沿う)ので、権限はメンバー以上とした
- **可視範囲**: 組織限定の問題は、その組織のメンバーだけが一覧・検索・直 URL で見られる。組織外からは 404(存在を漏らさない。D-017 方針 4 と同じ考え方)

### S-009 つまずき診断の出し方(暫定)

- **論点**: PROGRESS.md の改善候補 1「つまずきに応じたヒントの出し分け」を、どう作り、どこまで言うか
- **暫定採用**: 2 段構えで診断する。判定用の別実装は作らず、既存の judge をそのまま使う(SPEC.md §6)
  1. **構造チェック** — 回路の形だけで分かる抜け(コイルが無い / 期待されたデバイスを出力していない / 二重コイル / 自己保持の接点が無い / 発振)
  2. **最小修正の探索** — 学習者の回路に「1 手だけ」の修正を当てて判定し直し、全ケースが通ればその 1 手が原因。接点の種類・デバイス・タイマとカウンタの設定値・並列の縦線・条件の入れ忘れと入れすぎ を試す
- **言うのは「どこを」「どの方向に」まで**。「X1 を b 接点に変えてください」とは書かない。学習アプリなので、直す判断は本人に残す
- **1 回目の失敗では出さない**。すぐ手がかりを出すと自分で考える機会を奪う。同じ問題で 2 回目の失敗から出す
- **cells の意味を 2 つに分ける**: `kind: "repair"` は「そこを直せば通る」と言い切れるセル、`kind: "structure"` は話題にしているセル(このコイルが保持できていない、など)。structure のセルは間違っているとは限らないので、画面でも原因として指さない
- **却下**: 典型パターンを手書きのルールで並べる方式(回路の形に強く依存し、別解を間違いと呼んでしまう)、模範解答との差分を出す方式(答えそのもの。振る舞い判定の趣旨に反する)

**分かったこと(重要)**: 最小修正の探索は、テストケースが弱いと「意図とは違う 1 手」を原因だと言ってしまう。
実際、公式問題 `interlock-fix-2` のテストには「下降中に上昇ボタンを押しても切り替わらない」が無く、
相手出力の b 接点を上限リミットの b 接点に置き換えるだけでも全ケースが通ってしまっていた。
テストケースを 1 件足して塞いだ。**診断の精度はテストケースの強さそのもの**なので、
「診断が指すセルは模範解答と実際に違うセルである」を公式問題 30 問すべてで CI 検証している。

**速さ**: 候補ごとに判定を回すので、いちばん重い組み合わせ問題で 0.7 秒ほどかかる(他は 50 ms 以下)。
落ちているテストケースを落ちたステップまでで切り詰めたものでふるいにかけ、全ケース判定は落ちているケースから先に流して 1 件でも落ちたら打ち切る。
それでも一瞬止まって見えるので、画面側は判定結果を先に描いてから 1 フレーム遅らせて計算する。

### S-010 タイムチャートの記録方法(暫定)

- **論点**: PROGRESS.md の改善候補 4「シーケンス図・タイムチャート表示」を、判定のどこから取るか
- **暫定採用**: `runTestCase` に `recordTimeline` オプションを足し、**値が変わった時刻だけ**を記録する。既定は off
- **既定を off にする理由**: つまずき診断(S-009)は判定を何百回も回す。全部で波形を記録すると探索が目に見えて遅くなる。波形が要るのは画面に出す 1 ケースだけなので、そこで 1 回だけ記録しながら流し直す
- **記録するのは変化点だけ**: 3 秒待っても波形は増えない。矩形波は変化点さえあれば描ける
- **X も記録する**: 判定の観測値(`observe()`)は X を除くが、波形は入力の動きが見えないと読めない。`observeAll()` を別に用意した
- **同じ時刻に複数回変わったら、最後の値だけ残す**: settle は仮想時間を進めないので、1 つの時刻に何度も値が変わりうる。幅ゼロの区間は波形として描けないため、その時刻の最終値を採る。結果として「電源投入直後 OFF → 同じ時刻に X0 を押して ON」は ON だけが残る。待ってから押すケースなら初期状態にも幅ができて読める
- **横軸は仮想時間に比例**: 待ち時間の長いケースでは押した瞬間の変化が細くなるが、各ステップの時刻を下に文章で並べて補う

### S-011 「みんながつまずくところ」の集め方(暫定)

- **論点**: PROGRESS.md の改善候補 2「解説つきの間違い分類」。提出回路から「よくある誤答」をどう集めるか
- **暫定採用**: つまずき診断(S-009)の種類を分類キーにする。提出のたびにクライアントが診断の種類を一緒に送り、サーバーは**人数**を数える
- **なぜクライアントが送るのか**: 判定も診断もクライアント側で動く(SPEC.md §6)。診断はいちばん重い問題で 0.79 秒かかるので、Workers の CPU 予算(COST.md §1.1: 10 ms/リクエスト)ではサーバーで回せない。すでにクライアントの手元にある結果を送るのがいちばん安い
  - **代わりに失うもの**: クライアントは嘘の種類を送れる。サーバーは既知の ID かどうかしか検証できない。出るのは集計値だけで、誰かの不利益にはならないので、この段階では受け入れる。荒らされたら、分類をサーバー側の構造チェック(判定を回さない安いものだけ)に切り替える
- **数えるのは人数**。同じ人が同じ間違いを何度しても 1 人。`problem_mistake_users` に先に入れてみて、行が増えたときだけカウンタを足す。毎回 `submissions` を数え直すと読み取り行数を使いすぎる(D-018 / COST.md §1.2)
- **3 人に達するまで出さない**。1 人や 2 人の結果を「みんながつまずくところ」として見せるのは名前が嘘になるし、たまたま 1 人がした間違いを「よくある間違い」だと思い込ませてしまう。誰がしたかを推測しにくくする意味もある
- **出すのは 3 種類まで、畳んだ状態**。先に読むとどこを直せばいいかの見当がついてしまうので、開くかどうかは本人に決めてもらう
- **`DIAGNOSIS_IDS` は core に置き、値を消したり意味を変えたりしない**。DB に入る集計キーなので、変えると過去の集計が読めなくなる。足すときは末尾に追加する
- **却下**: 提出回路そのものをクラスタリングして分類する(回路の見た目が少し違うだけで別物になり、まとまらない)、サーバーで診断を回す(CPU 予算に入らない)

### S-013 オフライン対応のしかた(暫定)

- **論点**: PROGRESS.md の改善候補 6「PWA 化」。シミュレータ・判定・公式問題はすべてクライアント側にある(SPEC.md §6)ので、画面とアセットさえ手元にあれば未ログインの学習はオフラインで完結する。どう実現するか
- **暫定採用**: Service Worker を手書きする(`apps/web/public/sw.js`)。`vite-plugin-pwa` は入れない
  - **理由**: やることが「アセットを貯める」だけなので、ビルド設定と依存を増やす価値が見合わない。手書きなら何が起きているか全部読める
  - **代わりに失うもの**: ビルド時のファイル一覧(プリキャッシュ manifest)が無い。**初回訪問で通った分を貯める方式**になるので、Service Worker が画面を受け持つのは**次のページ読み込みから**。「初めて開いた直後にいきなり圏外」は効かない。これは Service Worker の仕様どおりの挙動でもある
- **キャッシュの方針**:
  - `/api/*` は**絶対にキャッシュしない**。古い進捗やランキングを見せると混乱するだけ。進捗も提出も投げっぱなしで送っている(S-002 / S-007)ので、失敗しても学習は止まらない
  - `/assets/*` は内容ハッシュ付きのファイル名なので中身が変わらない。キャッシュ優先で即返し、裏で取り直す
  - 画面の遷移はネットワーク優先。デプロイ直後に古い画面を掴まないため。つながらなければキャッシュした `index.html` を返す
- **初回のアセットを取りこぼさない工夫**: 初回訪問ではアセットの読み込みが登録より先に終わるので `fetch` では拾えない。画面側が自分の `<script>` / `<link>` の URL を Service Worker に `postMessage` で渡して貯めさせる
- **開発サーバーでは登録しない**。キャッシュが挟まると、直したはずの画面が出てこなくて悩むことになる
- **アイコンは SVG**。PNG を置くとバイナリを目視で確認できない。Chrome / Edge は SVG アイコンでもインストールできる。`purpose: "maskable"` 用は中央 60% の安全域に縮めた別ファイルにしている
  - **2026-09-16 追記: PNG も置く**。人間から「iPhone を持っていないので確認できない」と回答があった。iOS Safari は `apple-touch-icon` に SVG を受け付けず、指定しても無視してページの縮小画像をアイコンにしてしまう。確認できないままにするのではなく、確認が要らない形にした
    - SVG を正とし、**PNG はそこから作った出力**にする(`apps/web/scripts/build-icons.mjs`、`pnpm --filter @ladder-dojo/web icons`)。描画には E2E で入っている Playwright の Chromium を使う。手で描いた PNG を置かないので、「バイナリを目視で確認できない」は残るが「何がどう変わったか分からない」は起きない
    - `apple-touch-icon` 用(180px)だけは**角丸なし・不透明**にする。iOS は自前で角丸を掛けるので、こちらで角を透明にするとそこが黒く出る。背景に同じ色を敷いて角を埋めている
    - manifest は PNG(192 / 512 / maskable 512)を先に並べ、SVG も残す
    - **テストで見る**(`src/pwa-icons.test.ts`)。iPhone で確認できる人がいない以上、「参照を書き換えたのにファイルを置き忘れた」に気づく手段が他に無い。参照先が全部あるか、PNG として読めて指定どおりの大きさか、`apple-touch-icon` が PNG かを確かめている
- **却下**: `vite-plugin-pwa`(上記のとおり)、API レスポンスのキャッシュ(古いデータを見せるほうが害が大きい)、オフラインでの提出のキュー保存(進捗はすでに localStorage に残るので二重管理になる)

### S-014 CSV 書き出しの中身と作り方(暫定)

- **論点**: PROGRESS.md の改善候補 10「CSV 書き出し」。何を出すか、どう作るか
- **出すのは氏名と学習状況だけ。メールアドレスは入れない**。社内の報告に使うなら氏名で足りる。CSV は転送も複製も簡単なので、持ち出される個人情報は少ないほどよい
- **提出回路は出さない**。回路 JSON を Excel で開いても読めないし、行が極端に重くなる。回路は画面で見るもの
- **サーバーは変更しない**。画面に出している一覧表(改善候補 8 の `/matrix`)をそのまま縦持ちにするので、新しい API も D1 の読み取りも増えない
- **数式として実行されないようにする(CSV インジェクション)**: 表示名は本人が決められるので `=1+1` や `@SUM(...)` のような名前を付けられる。先頭が `= + - @ タブ 改行` のセルには `'` を足して文字列として読ませる
- **BOM を付ける**。付けないと Excel(Windows)が日本語を文字化けさせる
- **ファイル名は ASCII だけにする**: 日本語を含むファイル名だと、**保存名ごと失われる**ブラウザがある。Chromium で実測したところ `進捗.csv` が `download`(拡張子なし)で保存され、何のファイルか分からなくなった。組織名は ASCII 部分だけを使い、残らなければ `ladder-dojo-progress-YYYY-MM-DD.csv` にする。中身は UTF-8 + BOM なので日本語はそのまま読める
- **Blob の URL はすぐ捨てない**: `click()` の直後に要素を消したり URL を捨てたりすると、ダウンロードが始まる前に無くなる。30 秒後に片付ける

### S-015 画面ごとのバンドル分割と先読み(暫定)

- **論点**: PROGRESS.md の改善候補 11「バンドル分割」。JS が 1 つにまとまっていて、ビルドのたびに 500 KB 超の警告が出ていた。静的アセットは無料・無制限なので、費用ではなく初回表示の速さの話
- **画面ごとに `React.lazy` で分ける**。最初に出るのは公式問題の一覧なので、それだけを最初から持ち、残りは開くときに読む。結果は下のとおり

  | | 前 | 後 |
  |---|---|---|
  | 最初に読む JS | 565.04 kB(gzip 164.41) | 425.77 kB(gzip 126.31) |

- **問題一覧だけは分けない**。入口の画面を分けると、待ち画面を挟んでから本体を読むことになり、かえって遅くなる
- **分けた分は手が空いてから裏で全部取りに行く(`prefetchRoutes`)**。ここが S-013 との噛み合わせで、**分けただけだとオフラインが壊れる**。Service Worker は「通ったものを貯める」方式なので、一度も開いていない画面の JS はキャッシュに入らず、圏外でその画面を開くと真っ白になる。取りに行けば貯まるので、初回表示を軽くしたまま「一度も開いていない画面もオフラインで開ける」を保てる
- **先読みは `requestIdleCallback`(無ければ 2 秒後)**。最初の描画と帯域を取り合わせない。取りに行くのは 8 画面ぶんで合計 gzip 25 kB ほど
- **却下**: 手で `manualChunks` を書く(画面との対応が崩れやすく、分け方を間違えても気づけない)、リンクにカーソルが乗ったときだけ先読みする(スマホが主対象なのでカーソルが無い。またオフラインの担保にならない)
- **テスト**: E2E に「画面ごとに分けた JS は、裏で取りに行って貯まる」を追加した。キャッシュの中身を `expect.poll` で見る。先読みは時間で動くので、一度読んで判定すると並列実行で落ちる

### S-016 投稿問題の全文検索(暫定)

- **論点**: PROGRESS.md の改善候補 12。これまでの検索は `instr()` の全表走査で、投稿が増えると 1 回の検索で全行を読む(COST.md §1.2)
- **FTS5 を使う。トークナイザは `trigram`**。既定の `unicode61` は空白で語を切るので、分かち書きをしない日本語ではほとんど当たらない。trigram は 3 文字ずつの並びを索引にするので、日本語の部分一致がそのまま効く
- **ただし trigram は 3 文字未満に当たらない**。ローカルの D1 で実測したところ、「自己保持」「タイマ」「リセット」は当たるのに **「保持」「値」は 0 件**だった。日本語では「保持」「接点」「出力」「解除」のような 2 文字の語がごく普通に出てくる
- **なので置き換えではなく使い分ける**。3 文字以上は索引を引き、1〜2 文字はこれまでどおり `instr()` で拾う。**短い語で「0 件」になるより、遅くても当たるほうがよい**。全表走査が残るのは短い語のときだけで、今より悪くはならない
- **検索語は必ず引用符で囲んで渡す**。囲まないと `AND` `OR` `NOT` `NEAR` や `*` `^` `:` が検索の文法として解釈され、意図と違う結果になるか、文法エラーで 500 になる。中の引用符は 2 つ重ねて打ち消す
- **本体との同期はトリガで行う**。アプリ側で書き足す形にすると、書き込む場所が増えたときに片方だけ直して食い違う
- **更新のトリガは `UPDATE OF title, spec` に絞る**。絞らないと、いいねや挑戦回数を数え上げるたびに索引を書き直すことになる。あれは検索の中身と関係が無いうえ、投稿の更新よりずっと回数が多い(D1 の書き込みは 10万 行/日)
- **移行で既存の投稿を埋め戻す**。忘れると今ある問題だけ検索に出なくなる。テストは空の DB から始まるのでこの経路を通らない。索引の行を消してから埋め戻しの文を流す形でテストにした
- **索引を本当に引いているかをテストで見る**。索引の行だけを直接消して、それでも見つかるなら索引を使っていない、という形。全表走査に戻っても結果は同じなので、こうしないと気づけない
- **絞り込みは本体側に残す**(非公開・組織限定・通報による非表示)。索引は別の表なので、権限の判定を索引側に寄せると漏れる。索引は「候補を絞る」だけに使う
- **2026-09-16 確認済み**: 本番の D1 でも移行 0004 が通った(`Executed 6 commands`)。FTS5 と trigram が Cloudflare の D1 で使えることは、これで実機確認が取れた
- **却下**: `unicode61` + 形態素解析(D1 に日本語の辞書を持ち込めない)、外部の検索サービス(0円の制約。必要になれば COST.md に提案)、`content=` の外部コンテンツ表(本体の rowid に依存する。`posted_problems` の id は TEXT なので、素直に `problem_id` を持たせたほうが読み違えない)

### S-017 古い提出履歴の掃除(暫定)

- **論点**: PROGRESS.md の改善候補 13。COST.md §1.2 の縮退方針 段階2 に「90日以上前の不正解履歴を削除する Cron Trigger を有効化」とあるが、その Cron がまだ無い

- **却下**: 日数ではなく総量で切る(どのユーザーの履歴が消えるかが利用状況で変わり、説明できない)、`DELETE ... LIMIT`(SQLite の既定のビルドでは無効なので、主キーで絞る形にした)

### S-018 ラダー図のアクセシビリティ(暫定)

- **論点**: PROGRESS.md の改善候補 14。ラダー図は SVG で描いているので、**読み上げソフトには「ラダー図」としか伝わらない**。線と丸の集まりなので、中身は何も分からない。あわせて、通電表示に色だけの箇所が残っていた
- **読み上げ用の文章は `packages/core` で組み立てる**(`describe.ts`)。判定や診断と同じ理由で、DOM に依存しないほうがテストで固めやすい(D-002)。画面側は返ってきた文字列を `aria-label` に載せるだけにする
- **行ごとに読む**。「2 行 4 列のラダー図。1 行目、X0 の a 接点、Y0 の出力コイル。2 行目、…」。ラダー図は行が 1 つの回路なので、行を単位にするのが素直
- **配線は読まない**。「つながっている」ことは並び順で分かる。一つずつ読むと要素の間に「配線」が挟まって聞き取りにくい
- **分岐(縦線)は読む**。並列は回路の意味そのものなので、飛ばすと別の回路になってしまう
- **空の行も「何も置かれていません」と言う**。黙って飛ばすと、何行目の話をしているのか分からなくなる
- **動かしているときは行ごとに「通電中 / 無電圧」を添える**。止まっているとき(編集中)は言わない。動いていないのに通電の話をしても意味が無い
- **英数字と日本語の境目にだけ空白を入れる**(`ja()`)。「X0 の a 接点」は読みやすいが、「X0(起動ボタン) の 立ち上がり接点」は空白が余る
- **色だけに頼らない通電表示**: ここは元々、「電圧は来ているが流れていない」薄い橙と「無電圧」の灰色が、**同じ太さの実線で色だけ違っていた**。電流が流れている線は元から太くなるので形の差があったが、この 2 つには無かった。電圧が来ているだけの配線を**破線**にして、色の見分けがつかなくても区別できるようにした
- **テストの引き方**: E2E は `getByRole("img", { name: ... })` で引く。読み上げソフトが見るのと同じ道筋なので、見た目の作りを変えても「伝わるかどうか」だけを確かめ続けられる
- **却下**: SVG の各要素に `aria-label` を付けて回る(要素数だけ読み上げが発生して、かえって聞き取れない)、図の隣に文章を常時表示する(目で見る人には重複で、画面も狭くなる)

### S-019 通知の出しかた(暫定)

- **論点**: PROGRESS.md の改善候補 7「通知」。課題の割り当てや期限をどう知らせるか。当初はメールを想定していた

### S-020 画面の枠と見た目の決まりごと(暫定)

- **小さな部品は 1 か所に置く**(`ui.tsx`: `PageHeader` / `Card` / `Badge` / `buttonClass` など)。各画面が自前で角丸や影を書いていると、少しずつずれて「なんとなく揃っていない」画面になる

### S-022 「読む」の答え合わせで操作を再生する(暫定)

- **論点**: SPEC.md §3.2 (1) は「回答後に実際にシミュレータで動かして答え合わせをする」と書いている。実際にあったのは**自由操作のシミュレータだけ**で、設問が持っている操作列(`scenario`)はどこからも使われていなかった。学習者は設問と同じ操作を自分で組み立て直す必要があった
- **設問の操作列をそのまま再生する**。予測して選んだあと、**そのとおりになるのを目で見る**ところまでが 1 つの学習で、そこが「読む」の狙い(回路を目で追って動作を予測する力)
- **再生は core に置く**(`replay.ts` の `replayScenario`)。判定・診断・読み上げと同じで、DOM に依存しないほうがテストで固めやすい(D-002)
- **判定と同じ `StepRunner` を通す**。ここが要点で、**自分でスキャンを回してはいけない**。判定は「時間を進めたあと、状態が落ち着くまで回す」(S-005 の settle)。1 スキャンだけ見ると、まだ反映されていない途中の値を読む。実際、監査用に手で回したときに正しい問題を誤判定しかけた。同じ経路を通せば、答え合わせと判定がずれない
- **1 駒ずつ手で送る**。自動再生だと、変わった瞬間を見逃したときに戻れない。戻る・最初から も付ける
- **再生中は入力を触れないようにする**。駒どおりの状態を見せているので、触れると表示と中身がずれる。`DevicePanel` の `onToggleInput` を省略できるようにし、押せないときはボタンにしない(見た目だけ押せそうなものは壊れて見える)
- **自由操作も残す**。切り替えて自分で動かせる。再生だけだと「じゃあ X1 を押したら?」が試せない
- **却下**: 自動再生のみ(見逃したときに戻れない)、再生を web 側で実装する(判定とずれる。実際に一度ずれた)

### S-024 設問が切り替わったことを見せる(暫定)

### S-025 「直す」のヒントで「か所」と言わない(暫定)

- **論点**: 画面は「この回路には間違いが {bugCount} か所あります」と出していたが、**9 問中 5 問**は 1 つの不具合を直すのに **2〜4 マス**触る必要がある(例: `selfhold-fix-1` は自己保持の枝が無く、接点と縦線の 2 マスが要る)
- **`bugCount` は不具合の個数であって、直すマスの数ではない**。値そのものは間違っていない。**言い方が合っていなかった**
- **「か所」をやめる**。「直すべきところが 1 つあります。直すマスは 1 つとは限りません」にする。1 マス直して通らなかった学習者を「1 か所と言ったのに」で止めない
- **`bugCount` の意味をスキーマのコメントに明記する**。次に触る人が「マスの数」と取り違えないように
- **テスト**: `bugCount` が実際の差分マス数を超えないことを確かめる。超えていたら、直しようのない不具合を数えていることになる
- **却下**: `bugCount` を「直すマスの数」に変える(4 マスを「4 個の間違い」と言うのは実態と違う。自己保持の枝が無いのは 1 つの不具合)

### S-026 クリアした直後に「あなたのいま」を出す(暫定)

- **論点**: 問題をクリアしてもランキングに自分が出てこない、という報告。再現したところ**記録そのものは残っていた**。全体ランキングは Cron で 1 日 1 回しか作らない(D-010)ので、**スナップショットに載るのが翌日**なだけだった
- 「1 日 1 回更新されます」という説明は一覧の**下**にあり、まず目に入らない。**記録されていない**ように見える
- **全体ランキングを毎回その場で計算するのはやらない**。全ユーザーの集計は D1 の読み取り行数を大量に使う。日次スナップショットにした理由がそこにある(D-010)
- **本人 1 人ぶんだけ、その場で数え直して返す**(`GET /api/rankings` の `me`)。集計 SQL は対象ユーザーを絞れるので、読み取るのは自分の行だけ。費用は全体集計とまるで違う
- 画面では**一覧の上**に「あなたのいま」を出し、「いつ時点のスナップショットか」の説明も一覧の上へ移す
- 一覧が空のときの文言も「まだ記録がありません」から「まだ順位表ができていません(1 日 1 回作られます)」に変える。自分の記録はあるのに「記録がありません」と出るのを防ぐ
- **却下**: クリア時にスナップショットへ自分の行だけ差し込む(順位の整合が取れない。他人の値は古いままなので、割り込んだ行の順位が嘘になる)
- **却下**: Cron の間隔を短くする(読み取り行数が回数に比例して増える。0円の枠を削ってまで得るものではない)

### S-027 入力は押しボタンとして扱う(暫定)

- **論点**: 「カウンタ問題のシミュレータが間違っている気がする」という報告。**判定側は正しかった**(3 問 5 設問すべて、登録された正解とシミュレータの結果が一致することを確認)。おかしかったのは**自分で動かすときの入力の扱い**
- 入力 X はタップするたびに ON / OFF が入れ替わる**スイッチ**だった。X0 を 5 回タップすると ON→OFF→ON→OFF→ON で、**立ち上がりは 3 回**しかない。カウンタは 3 しか数えない。「5 回押したのに点かない」= シミュレータが壊れている、と見える
- 自分たちの E2E ですら「押して離す」を 2 回クリックで書いていた(`// 押しっぱなしだと 3 秒ごとに再点灯してしまうので、押して離す`)。**実物の押しボタンと合っていない合図**だった
- **入力は押しボタンにする**。押している間だけ ON、離すと OFF。問題文がどれも「押しボタン X0」「起動ボタン」と書いている以上、こちらが自然
- **一瞬のタップでも必ず 1 スキャンは ON にする**。押してすぐ離すと同じスキャンの中で ON と OFF が起きて立ち上がりが消えるため、離すのは「押した値が 1 回スキャンされたあと」まで待つ
- **センサやスイッチのように ON のままにしたいときのために「保持」を付ける**。「押しっぱなしでは 1 回しか数えない」を自分で確かめるのにも要る
- ラダー図の接点タップも同じ扱いにする。同じものを 2 通りに動かさない
- **カウンタ・タイマは現在値と設定値を並べて出す**(「3 / 5 回」「1.2 / 3.0s」)。現在値だけでは、あと何回で完了するのかが読めない
- **却下**: スイッチのままにして説明文だけ足す(「5 回押したのに 3 しか数えない」という驚きは説明では消えない)
- **却下**: タップを「押して離す」1 回ぶんに割り当てる(押しっぱなしを試せなくなる。カウンタ問題の設問 1 がまさにそれを問う)

### S-028 表記(アドレス体系と記号)を切り替えられるようにする(暫定)

- **論点**: 「記号をタブで切り替えられないか(オムロン・三菱のように)」という要望。現場で見ている書き方と違うと読みにくい、という動機は正しい
- **タブ名にメーカー名を使う**(2026-09-17 改訂、人間の判断)。当初は SPEC.md §3.1 の「特定メーカーの製品名・画面デザインは模倣しない」を理由に中立名(`X0 / Y0` / `0.00 / 100.00`)にしたが、**それでは自分の現場がどれに当たるのか分からない**。SPEC を改め、名前にメーカー名を使ってよいことにした(製品の画面・ロゴ・UI は模倣しない)
- 選択肢: `三菱系`(既定)、`オムロン系`、`IEC 61131-3`
- **名前がメーカーになった以上、中身も寄せる**。三菱系の設定値は `K5` / `K30`(タイマは 0.1 秒を 1 として数える)にした。`×5` のままでは、名前だけメーカーで中身が独自になる
- **「真似ではない」と画面に書く**。合わせているのは書き方だけで、機種ごとの仕様どおりではない。製品画面を模したものでもない
- **回路データは変えない。画面に出すときだけ書き方を変える**(`packages/core/src/notation.ts`)。判定・問題データ・API・診断はいっさい触らない。`DeviceId` は `[XYMTC] + 番号` のままなので、投稿問題・提出履歴・CSV との互換も切れない
- 切り替えるのは 4 つ: **デバイス名**(`X0` → `0.00`)、**設定値の書き方**(`K5` / `#0005` / `PV 5`)、**立ち上がり接点の中の記号**(`↑` / `P`)、**文章の中のデバイス名**
- **図だけ切り替えて問題文を放置しない**。「0.00 を押すと」と図に書いてあるのに問題文が「X0 を押すと」では照合できない。問題文・設問・選択肢・解説・ヒント・読み上げ用の説明・波形・テスト結果の差分まで通す
- ワード.ビットの割り付け(入力 0 ワード目、出力 100 ワード目、内部リレー W)は**よくある一例**であって特定機種の仕様ではない。画面の説明にもそう書く
- IEC ではデバイス名を変えない。**規格は変数名の付け方を決めていない**(利用者が付ける)ので、`X0` はそのまま変数名として通る
- 端末ごとの好みなので **localStorage に持つ**。ログインは要らないし、サーバーに送れば D1 の書き込みを使うだけで得がない
- **やらないこと**: タイマ・カウンタを IEC のファンクションブロック(TON / CTU の四角い箱)で描くのは今回は見送る。ラングの形が変わるので、描画の作り直しが要る。必要になったら別で
- **通すのを忘れやすい**。実装後のレビューで、つまずき診断の文章とログイン前の紹介文が変換から漏れていた。どちらも**すぐ横に変換済みのラダー図がある**場所で、図と文章が食い違っていた。デバイス名を画面に出す場所を足したら、必ず変換を通す
- **却下**: 立ち上がり接点を「上向きの山」のまま置く(標準の `P` とも国内の `↑` とも違う独自記号だった。どちらかに寄せる)
- **動いているときの現在値は秒のまま出す**。ラダー図の設定値は `K30` でも、デバイス一覧のタイマは `1.2 / 3.0s` と秒で出す。刻み数(`12 / 30`)にすると**いま何秒経ったのかが読めない**。表記を揃えることより、動きが読めることを優先する
- **やらないこと(2)**: 三菱の FX 系は入出力の番号が 8 進(X7 の次が X10)だが、**番号は 10 進のまま**にした。機種によって 8 進・16 進と分かれるうえ、番号の付け方まで変えると編集画面の番号選びと食い違って見える。公式問題は X0〜X4 しか使わないので表示上の差も出ない
