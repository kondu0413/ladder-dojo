# COST.md — ランニングコストと無料枠

SPEC.md §2.3 に基づく。**現在の月額ランニングコスト: 0円**(全サービス無料プラン、クレジットカード登録なし)。

有料化が必要と判断した場合は、実装せずに本ファイル末尾の「課金提案」に追記して人間の承認を待つ。

> **数値の出典について**: 以下の無料枠の数値は 2026-09-14 時点で Claude Code が把握している値であり、この環境からは各社の料金ページを参照できなかった。
> 人間がセットアップ時(SETUP.md)に各社の料金・制限ページで数値を確認し、「確認日」欄を埋めること。差があればこのファイルを修正する。
> 確認先: Cloudflare Workers → https://developers.cloudflare.com/workers/platform/limits/ と /workers/platform/pricing/、D1 → https://developers.cloudflare.com/d1/platform/limits/ と /d1/platform/pricing/

> **2026-09-14 改訂**: Supabase・Brevo を廃止し、Cloudflare Workers + D1 に一本化(DECISIONS.md D-006)。使うサービスは Cloudflare・Google Cloud・GitHub の3つ。

## 1. サービス別 無料枠と縮退方針

### 1.1 Cloudflare Workers(ホスティング + API)— Workers Free プラン

SPA の静的ファイルと Hono API を 1 つの Worker `ladder-dojo` で配信する(D-009)。

| 項目 | 無料枠(要確認) | 本アプリの想定消費 | 確認日 |
|---|---|---|---|
| Worker リクエスト数 | **10万 リクエスト / 日**(アカウント全体、UTC 0時にリセット) | `/api/*` のみカウント。1ユーザー1セッションあたり API 呼び出し 10〜30 回。1日 300 ユーザー × 30 回 = 9,000 | |
| 静的アセットへのリクエスト | **無料・無制限**(上記 10万 に数えない) | 画面表示・シミュレータ・公式問題は全てここ。未ログイン利用は Worker を一切消費しない | |
| 短時間のリクエスト上限 | 1,000 リクエスト / 分 | 授業で 40 人が同時にログインしても ≈ 数百 / 分 | |
| CPU 時間 | **10 ms / リクエスト** | 通常の API は 1〜3 ms。フェーズ2 の投稿公開時のサーバー側再検証(core のシミュレータ実行)が最も重い | |
| メモリ | 128 MB / Worker | 十分 | |
| Worker のサイズ(圧縮後) | 3 MB | Hono + Better Auth + Drizzle + core で 数百 KB 見込み。Prisma 等の重い ORM を避ける理由(D-018) | |
| サブリクエスト数 | 50 / リクエスト | Google の OAuth トークン交換で 2〜3。D1 クエリもここに数える(D1 §1.2 参照) | |
| Worker 数 | 100 / アカウント | 1(必要になれば preview 用にもう 1 つ) | |
| 環境変数 / シークレット | 64 個 / Worker、1 つ 5 KB | 5 個程度 | |
| Cron Triggers | 利用可(アカウントあたり 5 個、要確認) | フェーズ3 のランキング集計で 1〜2 個 | |
| `workers.dev` サブドメイン | 無料、1 アカウント 1 つ | `https://ladder-dojo.<サブドメイン>.workers.dev` を本番 URL にする(独自ドメインは 0円制約外) | |
| 静的アセット | 20,000 ファイル / Worker、1 ファイル 25 MiB | 数百ファイル、最大でも JS バンドル 1〜2 MB | |
| Workers Logs | 20万 イベント / 日、保持 3 日 | エラー時のみログ出力する | |
| 商用利用 | 制限なし | 将来の企業導入を塞がない | |

**上限超過時の挙動(要確認)**: 10万 リクエスト/日 を超えると、その日の残り時間は `/api/*` がエラーを返す。静的アセットは Worker を通らないため **画面・シミュレータ・公式問題は使い続けられる**。アプリ側は API エラー時に「保存できません(しばらくして再試行)」を表示し、未ログイン相当の動作に落とす(S-002 の localStorage を使う)。

**縮退方針(上限の 70% で発動)**

| 逼迫する項目 | 段階1(0円で対処) | 段階2(0円で対処) | 段階3(課金提案) |
|---|---|---|---|
| 10万 req / 日 | 進捗の保存を「問題クリア時・画面離脱時」にまとめる(試行ごとに送らない)。セッション確認は Cookie キャッシュ(D-018)で API を呼ばない。TanStack Query の `staleTime` を延長 | 一覧系 API のレスポンスを Cache API(無料)で 60 秒キャッシュ。ランキングは Cron で生成した JSON を静的アセット相当として返す | Workers Paid(月額 5 USD、1,000万 req/月 込み)を提案 |
| CPU 10 ms | サーバー側再検証にテストケース数・スキャン数の上限(1 問あたり 20 ケース × 1,000 スキャン)と `AbortSignal` によるタイムアウトを設ける | 再検証結果を回路ハッシュでキャッシュし、同一回路は再実行しない | Workers Paid(30 秒 CPU)を提案 |
| 1,000 req / 分 | フロントの再試行に指数バックオフを入れる | — | Workers Paid を提案 |
| Worker サイズ 3 MB | 依存の見直し(バンドル分析)、core のツリーシェイク | — | Workers Paid(10 MB)を提案 |

### 1.2 Cloudflare D1(データベース)— Workers Free プラン

| 項目 | 無料枠(要確認) | 本アプリの想定消費 | 確認日 |
|---|---|---|---|
| 読み取り行数 | **500万 行 / 日** | インデックスを使う前提で、1 API 呼び出しあたり 1〜50 行。1日 9,000 呼び出し × 20 行 = 18万 | |
| 書き込み行数 | **10万 行 / 日** | 進捗 upsert 1 行 + 提出 1 行 + 活動日 1 行 = 1 試行あたり ≈ 3 行。1日 3,000 試行で 9,000 | |
| ストレージ合計 | **5 GB / アカウント** | 回路JSON 2〜5 KB × 提出履歴が主。ユーザー1,000人・提出2万件で ≈ 100 MB | |
| **1 データベースの最大サイズ** | **500 MB(Free)**。Paid は 10 GB | 本番は 1 DB なので実効上限はこちら。S-003 の履歴上限と縮退方針で管理 | |
| データベース数 | 10 / アカウント | 1(本番)。ローカル D1 は数えない | |
| Time Travel(時点復元) | **7 日間(Free)**。Paid は 30 日 | バックアップの第1系統(D-015)。週次 export で補完 | |
| **1 リクエスト(Worker 呼び出し)あたりのクエリ数** | **50(Free)**。Paid は 1,000。Worker のサブリクエスト上限(§1.1)と共通枠で、`prepare().run()` / `all()` / `first()` の 1 回が 1 クエリ、`batch()` は 1 回として数える(要確認) | 1 API 呼び出しで 1〜5 クエリに抑える。**一覧 API でループ内クエリ(N+1)を書くと、件数 50 前後で即エラーになる**ため、JOIN または `batch()` / `IN (...)` でまとめる(D-017 の設計方針 7) | |
| 1 行・1 文字列の最大サイズ | 2 MB | 回路 JSON は数 KB。API 層で 256 KB 上限を設ける | |
| SQL 文の最大長 / バインド数 | 100 KB / 100 個 | 一括 insert は 20 行ずつに分割 | |
| クエリの最大実行時間 | 30 秒 | — | |
| テーブルの列数 | 100 | — | |
| 一時停止 | **なし**(無アクセスでも停止しない) | keep-alive 不要 | |

**クエリ回数上限の注意(Free 50 回 / リクエスト)**: この上限は日次枠ではなく **1 リクエストごと**に効き、超えた瞬間にそのリクエストが失敗する(縮退で逃げられない)。「組織メンバー 60 人の進捗を 1 人ずつ SELECT」のような N+1 は本番で必ず落ちる。設計時点で JOIN・`IN (...)`・`batch()` に統一し、API テストで 1 リクエストあたりのクエリ回数を検査する(D-017)。

**行数課金の注意**: D1 の「読み取り行数」はクエリが**走査した行数**で数える。インデックスの無い `WHERE` や `COUNT(*)` はテーブル全体を読む。全テーブルに `user_id` 先頭の複合インデックスを張り、件数は集計列で持つ(D-018)。

**上限超過時の挙動(要確認)**: 読み書きの日次上限を超えると、その日の残り時間は D1 のクエリがエラーになる(Free プランでは従量課金に移行しない)。Workers と同じく、画面と公式問題は使えるので「保存できない」状態に落とす。

**縮退方針(上限の 70% で発動)**

| 逼迫する項目 | 段階1(0円で対処) | 段階2(0円で対処) | 段階3(課金提案) |
|---|---|---|---|
| DB 500 MB(1 DB) | 提出履歴の保持上限を「不正解 直近20件」→「直近5件」に下げる(S-003)。回路JSONを正規化して重複を除去 | 90日以上前の不正解履歴を削除する Cron Trigger を有効化。サンドボックス保存数に上限(1ユーザー50件)を設ける。それでも足りなければ提出履歴だけ 2 つ目の D1(`ladder-dojo-history`)に分離(合計 5 GB まで) | Workers Paid(月額 5 USD、1 DB 10 GB)を提案 |
| 読み取り 500万 行 / 日 | 走査行数の多いクエリを Workers Logs で特定しインデックス追加。一覧のページサイズを縮小 | 一覧・ランキングを Cache API でキャッシュ。ランキングは Cron で 1 日 1 回の集計に落とす | Workers Paid(250億 行/月 込み)を提案 |
| 書き込み 10万 行 / 日 | 試行ごとの進捗 upsert をクリア時・離脱時にまとめる。`activity_days` は 1 日 1 回だけ書く | 不正解の提出回路を保存しない(正解のみ保持)モードに切替 | Workers Paid(5,000万 行/月 込み)を提案 |
| Time Travel 7 日 | 週次 export(D-012)を保持 4 世代に増やす | — | Workers Paid(30 日)を提案 |
| クエリ 50 回 / リクエスト | 該当 API を JOIN / `batch()` に書き直す(縮退ではなく不具合として修正)。ページサイズを 20 件に固定 | 重い集計は Cron Triggers で事前計算した集計テーブルを 1 クエリで読む | Workers Paid(1,000 回)を提案。ただし通常は設計で回避でき、課金理由にはならない |
