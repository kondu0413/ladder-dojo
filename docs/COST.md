# COST.md — ランニングコストと無料枠

SPEC.md §2.3 に基づく。**現在の月額ランニングコスト: 0円**(全サービス無料プラン、クレジットカード登録なし)。

有料化が必要と判断した場合は、実装せずに本ファイル末尾の「課金提案」に追記して人間の承認を待つ。

> **数値の出典について**: 以下の無料枠の数値は 2026-09-05 時点で Claude Code が把握している値であり、この環境からは各社の料金ページを参照できなかった。
> 人間がアカウント作成時(SETUP.md)に各社の料金ページで数値を確認し、「確認日」欄を埋めること。差があればこのファイルを修正する。

## 1. サービス別 無料枠と縮退方針

### 1.1 Supabase(認証・DB)— Free プラン

| 項目 | 無料枠(要確認) | 本アプリの想定消費 | 確認日 |
|---|---|---|---|
| アクティブなプロジェクト数 | 2 プロジェクト / 組織 | dev + prod で 2 つ使い切る | |
| データベース容量 | 500 MB / プロジェクト | 回路JSON 2〜5KB × 提出履歴が主。ユーザー1,000人・提出2万件で ≈ 100 MB | |
| 認証 月間アクティブユーザー(MAU) | 50,000 MAU | フェーズ3でも数百〜数千 | |
| ファイルストレージ | 1 GB | **使わない**(画像アップロード機能なし) | |
| 帯域(egress) | 5 GB / 月 | API 応答のみ(静的ファイルは Cloudflare)。1リクエスト 5KB × 100万回 = 5GB が目安 | |
| Edge Functions | 50万回 / 月 | **使わない**(D-010) | |
| Realtime | 同時接続 200 / メッセージ 200万 / 月 | **使わない**(フェーズ3まで不要) | |
| 組み込みメール送信 | 約 2 通 / 時、送信先制限あり | 使わない。カスタム SMTP(Brevo)を使う | |
| ログ保持 | 1 日 | 調査は当日中に行う | |
| 自動バックアップ | **なし** | CI で週1回 `pg_dump` を保存(D-012) | |
| 非アクティブ時の一時停止 | **7 日間アクセスがないと停止** | CI の keep-alive で防止(D-015) | |
| API リクエスト数 | 無制限(ただし egress とコンピュートに依存) | — | |
| 認証レート制限 | メール送信 30 通/時(カスタムSMTP時)、OTP 等に別途上限 | ログインは Google 主導線で回避 | |

**縮退方針(上限の 70% で発動)**

| 逼迫する項目 | 段階1(0円で対処) | 段階2(0円で対処) | 段階3(課金提案) |
|---|---|---|---|
| DB 500 MB | 提出履歴の保持上限を「不正解 直近20件」→「直近5件」に下げる(S-003)。回路JSONを正規化して重複を除去 | 90日以上前の不正解履歴を削除する `pg_cron` ジョブを有効化。サンドボックス保存数に上限(1ユーザー50件)を設ける | Pro プラン(月額 25 USD、8 GB)を提案 |
| egress 5 GB | 一覧 API のページサイズを縮小、TanStack Query のキャッシュ時間を延長 | 投稿問題一覧を Cloudflare Pages Functions 経由でキャッシュ(Cache API、無料) | Pro プラン(250 GB)を提案 |
| MAU 50,000 | — (到達時点で運用規模が変わっているため段階1なし) | — | Pro プラン(10万 MAU)を提案 |
| 一時停止された | ダッシュボードで Restore(1クリック、数分)。SETUP.md §9 参照 | keep-alive の頻度を上げる | — |
| プロジェクト数 2 | dev を削除して prod のみにし、E2E は Supabase CLI ローカルスタック(Docker)に移す | — | — |

### 1.2 Cloudflare Pages(ホスティング)— Free プラン

| 項目 | 無料枠(要確認) | 本アプリの想定消費 | 確認日 |
|---|---|---|---|
| 静的配信の帯域・リクエスト | **無制限** | — | |
| ビルド回数 | 500 回 / 月 | **0 回**(CI からの Direct Upload デプロイはビルド回数を消費しない) | |
| 同時ビルド | 1 | — | |
| ファイル数 / サイト | 20,000 | 数百 | |
| 1ファイル上限 | 25 MiB | 最大でも JS バンドル 1〜2 MB | |
| プロジェクト数 | 100 | 1 | |
| カスタムドメイン | 100 / プロジェクト | 0(`*.pages.dev` を使う。ドメイン購入は 0円制約外) | |
| Pages Functions(Workers 無料枠) | 10万リクエスト / 日、CPU 10 ms / リクエスト | フェーズ2の投稿公開時の再検証のみ。1日数十〜数百 | |
| Cron Triggers | 利用可(Workers 無料枠内) | ランキング更新の代替として予備 | |
| プレビューデプロイ | 無制限(ブランチごと) | PR ごとに 1 つ | |

**縮退方針**

| 逼迫する項目 | 段階1 | 段階2 | 段階3 |
|---|---|---|---|
| Functions 10万 req/日 | 再検証はクライアントで先に実行し、サーバーは「公開ボタン押下時」のみ呼ぶ(既にその設計) | 再検証結果をキャッシュし、同一回路ハッシュは再実行しない | Workers Paid(月額 5 USD)を提案 |
| CPU 10 ms | 検証タイムアウトを設け、テストケース数・スキャン数に上限(1問あたり 20 ケース × 1,000 スキャン)を設ける | — | — |

### 1.3 GitHub(リポジトリ・CI)— Free プラン(private リポジトリ)

| 項目 | 無料枠(要確認) | 本アプリの想定消費 | 確認日 |
|---|---|---|---|
| Actions 実行時間 | **2,000 分 / 月**(private。public なら無制限) | CI 1 回 ≈ 6〜8 分(E2E 含む)。1日 5 回で ≈ 1,000 分/月 | |
| Actions ストレージ(アーティファクト・キャッシュ) | 500 MB | pnpm キャッシュ + Playwright ブラウザ + pg_dump | |
| スケジュール実行 | 利用可。**60 日間リポジトリに活動がないと自動で無効化** | keep-alive / backup に使用 | |
| Secrets | 無制限(1 つ 48 KB まで) | 約 10 個 | |

**縮退方針**

| 逼迫する項目 | 段階1 | 段階2 | 段階3 |
|---|---|---|---|
| 2,000 分 / 月 | E2E は PR と main のみで実行し、push ごとの CI は lint + unit のみに絞る。Playwright はモバイル 1 プロファイルで回す | E2E を夜間 1 回のスケジュール実行に集約。`concurrency` で古い実行をキャンセル | **リポジトリを public にする**(0円で無制限化。人間の判断) or GitHub Pro(月額 4 USD、3,000 分) |
| ストレージ 500 MB | pg_dump は圧縮し保持 4 世代に限定。Playwright ブラウザはキャッシュせず毎回インストール(時間と交換) | — | — |
| スケジュール停止 | 人間が Actions タブで再有効化 | keep-alive を Cloudflare Cron Triggers に移す | — |

### 1.4 Brevo(認証メール SMTP)— Free プラン

| 項目 | 無料枠(要確認) | 本アプリの想定消費 | 確認日 |
|---|---|---|---|
| 送信数 | 300 通 / 日 | 新規登録の確認メール + パスワードリセット。1日数通〜数十通 | |
| 送信者 | メールアドレス単体の検証で可(独自ドメイン不要) | 人間のメールアドレスを送信者にする | |
| SMTP リレー | 利用可 | Supabase Auth のカスタム SMTP に設定 | |
| 備考 | 無料プランは送信メールに Brevo のロゴが入る | 認証メールなので許容 | |

**縮退方針**

| 逼迫する項目 | 段階1 | 段階2 | 段階3 |
|---|---|---|---|
| 300 通 / 日 | Google ログインを UI で優先表示し、メール登録を「その他の方法」に下げる | 登録フォームにレート制限(Supabase Auth 側の設定) | Brevo Starter(月額 約 9 USD)または独自ドメイン + Resend を提案 |
