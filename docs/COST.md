**取得ループの修正(2026-09-18 / S-037)**: ログイン中に `GET /api/progress` が止まらずに飛び続ける不具合があった(実測 **4 秒で 427 回**、1 人あたり毎秒 100 回)。上の表の「1 セッションあたり 10〜30 回」は、この不具合がある限り成り立たず、**1 人が画面を開いたままにすると 10 万リクエスト/日を 20 分ほどで使い切る**。D1 の読み取り行数も同じ勢いで減る。修正後は 1 セッション 1 回に戻った。見た目の作り直し(S-036)は静的アセットの変更だけなので、費用は変わらない。

**Web Push の通知(2026-09-18 / S-045)**: 課題の期限と新しい課題を毎朝 1 回、購読している人に送る。外部サービスは使わず、Workers の WebCrypto で暗号化してプッシュサービス(ブラウザ側の URL)へ fetch する。費用の当たりどころは **1 回の Cron 実行のサブリクエスト 50** で、D1 のクエリ(最大 6)と送信(1 通 1 回)を合わせてここに収める。送信は **40 通で打ち切る**(打ち切ったら警告ログ)。日次のリクエスト数には Cron 1 回 + 送信数しか乗らないので、10 万/日に対しては誤差。購読の登録は D1 の書き込み 1 行(1 端末 1 回)。**打ち切りが続くようになったら**、送信を朝と夕の 2 回に分ける(Cron を 1 本足す。5 個までは無料)か、Workers Paid(サブリクエスト 1,000)を提案する。

**上限超過時の挙動(要確認)**: 10万 リクエスト/日 を超えると、その日の残り時間は `/api/*` がエラーを返す。静的アセットは Worker を通らないため **画面・シミュレータ・公式問題は使い続けられる**。アプリ側は API エラー時に「保存できません(しばらくして再試行)」を表示し、未ログイン相当の動作に落とす(S-002 の localStorage を使う)。

**検索について**(2026-09-16 更新): FTS5 仮想テーブル `posted_problems_fts`(trigram)に移した。**ただし 3 文字以上の検索語だけ**。trigram は 3 文字未満に当たらず、日本語では「保持」「接点」のような 2 文字の語がごく普通に出てくるので、1〜2 文字はこれまでどおり `instr()` の全表走査で拾う(S-016)。`LIKE` は SQLite のパターン長上限(既定 50 バイト = 日本語 16 文字)に当たって 500 になるため使わない。

- **読み取り行数**: 3 文字以上の検索は索引を引くので、投稿数に比例して増えない。全表走査が残るのは 1〜2 文字の検索のときだけ
- **書き込み行数**: 索引の更新は投稿・削除・題名/説明の修正のときだけ。**いいねや挑戦回数の数え上げでは書き直さない**(トリガを `UPDATE OF title, spec` に絞っている)
- **サイズ**: 索引は題名と説明の写しを持つ。D1 の 5 GB に対しては誤差

**クラス全体の進捗表(2026-09-16 追記)**: メンバー数 × 触った問題数だけ読む。メンバー 50 人・進捗 2,000 行を上限にしているので、1 回の表示で読むのは最大 2,050 行。管理者しか開かない画面なので、回数も限られる。

**「みんながつまずくところ」の読み書き(2026-09-15 追記)**: 集計は `problem_mistakes` に人数を持たせてあるので、表示は 1 問につき最大 3 行の読み取りで済む(`submissions` は数えない)。書き込みは不正解の提出 1 件につき最大 2 行(重複よけ 1 + カウンタ 1)で、同じ人の 2 回目からは 0 行。

**フェーズ3 で増えた書き込み**: 全体ランキングの日次スナップショット(Cron、03:00 JST)が 1 指標 × 1 期間あたり上位 50 行。組み合わせは 10 通りなので **1 日 500 行**。10万 行/日 の上限に対して 0.5% で、常時アクセスが無くても発生する唯一の書き込み。組織内ランキングはその場で計算するので書き込み 0。

**ランキングの「あなたのいま」(2026-09-16 追加 / S-026)**: 全体ランキングを開いたとき、ログイン中の本人 1 人ぶんだけ集計をその場で走らせる。対象を `user_id` で 1 人に絞るので走査するのは自分の行だけ(進捗・投稿挑戦を合わせて数十行、連続学習日数でも 90 日ぶんの活動日)で、クエリは 1 本増える。**全体集計をその場でやる案とは費用が桁で違う**ので、日次スナップショット(D-010)はそのまま残す。ランキング画面は 1 セッションに数回しか開かれない想定で、読み取り行数への影響は誤差。

**入力を押しボタンにした件(2026-09-17 / S-027)**: シミュレータはブラウザ側だけで動く(SPEC.md §6)。スキャンの回数も requestAnimationFrame のままで変えていないので、Workers にも D1 にも影響はない。**費用は変わらない。**

**表記の切り替え(2026-09-17 / S-028)**: 選んだ表記は端末の localStorage に持ち、サーバーには送らない。変換はすべてブラウザ側。**Workers も D1 も使わないので費用は変わらない。**

**投稿時の再検証の CPU(2026-09-17 / S-030)**: 投稿すると、模範解答がテストを通ることを Workers の中で確かめる。ここがアプリで最も CPU を使う。**実測で判定を 2.6 倍速くした**(当時の公式問題 35 問の合計 227ms → 89ms、最重量 33ms → 12.8ms)。上限は「1 問ぜんぶの合計スキャン数」で抑える(1 ケースずつ短くても 20 件積めば同じだけ使うため)。

- **ただし 1 スキャンの費用はこの開発環境での実測(1〜6 マイクロ秒)で、Workers 上では測れていない。** 本番で投稿がエラーになるようなら、まず `PUBLISH_LIMITS.maxScansTotal` を下げる
- 1 ケースの上限は、テストケースのスキーマが許す長さ(合計 120 秒)より必ず広くしておく。狭いと「スキーマ上は正しいのに投稿できない」問題が生まれる

**提出回路の書き込み**: 2026-09-15 のフェーズ3 で、答え合わせのたびに提出回路を保存するようになった(S-007)。上の表の「1 試行あたり ≈ 3 行」はこれを見込んだ数字なので、想定は変えていない。同じ回路の連投は指紋一致で弾く(S-003)ので、行は増えない。

**行数課金の注意**: D1 の「読み取り行数」はクエリが**走査した行数**で数える。インデックスの無い `WHERE` や `COUNT(*)` はテーブル全体を読む。全テーブルに `user_id` 先頭の複合インデックスを張り、件数は集計列で持つ(D-018)。

**上限超過時の挙動(要確認)**: 読み書きの日次上限を超えると、その日の残り時間は D1 のクエリがエラーになる(Free プランでは従量課金に移行しない)。Workers と同じく、画面と公式問題は使えるので「保存できない」状態に落とす。

**提出履歴の掃除について**(2026-09-16 追加 / S-017): 90 日より前の不正解を消す Cron を、**閾値を待たず常時**動かしている(1 日 1 回、ランキング集計と同じ `"0 18 * * *"`)。動かす仕組みが無い状態で「いざとなったら有効化する」と書いてあるのは、無いのと同じだったため。

- 消すのは**不正解だけ**。正解は残す(「いつ解けたか」は本人の記録として意味がある)
- **1 回の実行で 2,000 件まで**。溜まったぶんを一度に消すと、D1 の書き込み(10万 行/日)を掃除だけで使い切りかねない。残りは翌日以降に回る
- 上限に当たったときだけログに残す。**当たり続けるなら、溜まる速さに掃除が追いついていない合図**なので、この表の見直しが要る
- 保持日数 90 日と 1 回 2,000 件は実測のない見込みの値。月次確認(§2)で見直す

|---|---|---|---|

## 3. 課金提案(承認待ち)

### 提案 #1: メール通知のための独自ドメイン(2026-09-16)

改善候補 7「通知」(課題の割り当て・期限の連絡)をメールで行う場合に必要。

- **必要な理由**: **送信元にできるドメインが無い**。`workers.dev` のサブドメインには SPF / DKIM の DNS レコードを置けないので、`@ladder-dojo.mojya.workers.dev` から送ることはできない(Cloudflare 自身のドキュメントに明記)。2024 年 2 月以降、Gmail / Yahoo / Microsoft は送信ドメインの認証を必須にしており、**認証が無い送信は届かないか、差出人が別のアドレスに書き換えられる**
- **サービス・プラン・月額**:
  - **独自ドメイン: 年 1,000〜2,000 円程度**(.com / .net。レジストラによる)。これが唯一の必須費用
  - 送信サービスは**ドメインさえあれば 0円で足りる**。Resend の無料枠が 3,000通/月・100通/日・検証済みドメイン 1 つ。このアプリの想定(課題の割り当てと期限の連絡)なら十分
- **無料の代替案とその欠点**:

  | 案 | 費用 | 欠点 |
  |---|---|---|
  | **Web Push(PWA の通知)** | **0円** | メールではないので、アプリを一度も開いていない人には届かない。iOS はホーム画面に追加していないと受け取れない。**ただし外部サービスが要らず、既にある Service Worker(S-013)の上に載る** |
  | アプリ内のお知らせ一覧 | 0円 | 開かないと気づかない(通知にならない) |
  | Brevo の無料枠をドメイン無しで使う | 0円 | **差出人が `@brevosend.com` に書き換えられる**。受け取る側から見て誰からのメールか分からず、迷惑メール扱いされやすい。製品の通知としては使えない |
  | Cloudflare Email Sending | **不可** | 2026-04 に public beta になったが **Workers Paid($5/月)必須で無料枠なし**。ドメインも別途要る |
  | MailChannels の Workers 無料枠 | **消滅** | 2024 年に終了済み(D-008 を書いた当時の前提) |

- **おすすめ**: **まず Web Push を 0円で作る**。メールが要ると分かってからドメインを買う。ドメインは年単位の固定費なので、使う当てが立ってからでよい
